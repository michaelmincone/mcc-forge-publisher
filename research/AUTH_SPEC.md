# Native macOS authentication specification

Reviewed 2026-10-12. Initial research used public sources only. A subsequent explicitly authorized native probe called device authentication and SISU begin with this app's generated proof key; it stopped before user credentials, Xbox user/XSTS exchange, or PlayFab login. No browser cookies or cached game tokens were read. The implementation uses interactive Microsoft sign-in, an authorization code and PKCE, native HTTP, and native cryptography. It never collects a password or rotates identity after a service refusal.

## Evidence and application identity

Default compatibility profile reproduces the public [HaloCache auth implementation](https://github.com/HaloCache/halo-mcc-auth/tree/50c5054805b5f52fafc2ddcb8aeaa1f97d149443): public OAuth client ID `000000004825fc1f`, Xbox title ID `1144039928`, redirect `https://login.live.com/oauth20_desktop.srf`, scopes `xboxlive.signin offline_access`, device profile `Win32` / `10.0.19045`, sandbox `RETAIL`. These identifiers are not an app secret. Their public availability and successful user consent do not establish Microsoft's approval of a separate native publisher. The default must be documented as unofficial compatibility, and server denials must stop the flow.

Custom registrations must consistently supply their own client ID, title ID, redirect, and permitted device profile to every stage. HaloCache's `beginAuth` permits a client-ID override, but its redemption, authorization, and refresh methods still hardcode MCC's ID; do not reproduce that inconsistent behavior. No official source retrieved here guarantees that an arbitrary registration can acquire MCC title claims or access PlayFab `EE38`. [PlayFab's Xbox title association](https://learn.microsoft.com/en-us/xbox/playfab/identity/player-identity/platform-specific-authentication/xbox-live-add-on) can restrict accepted Xbox title tokens. MCC's actual policy remains unknown.

For an independently registered native identity, [Microsoft's desktop registration guidance](https://learn.microsoft.com/en-us/entra/identity-platform/scenario-desktop-app-configuration) supports a Mobile/Desktop public client and `msauth.<bundle-id>://auth` for Swift/macOS. [MSAL redirect guidance](https://learn.microsoft.com/en-us/entra/msal/objc/redirect-uris-ios) requires registering that URI and its scheme in the app. A system-browser loopback alternative uses a registered localhost redirect. [Redirect restrictions](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url) require registered URI matching, distinguish paths, ignore ports only for localhost matching, and disallow registered query parameters for personal Microsoft accounts. These options cannot be substituted into MCC's compatibility registration without evidence that it allows them.

[Microsoft's auth-code specification](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow) supports PKCE, matching callback state, native public clients without secrets, and refresh-token replacement. Its `consumers` endpoints are `https://login.microsoftonline.com/consumers/oauth2/v2.0/authorize` and `/token`. The [Xbox website documentation](https://learn.microsoft.com/en-us/gaming/gdk/docs/services/fundamentals/s2s-auth-calls/service-authentication/live-website-authentication) documents registered Microsoft-account sign-in, user-token exchange, and XSTS. It spells its refresh scope `XboxLive.offline_access`; HaloCache's legacy profile uses `offline_access`. Keep scope sets tied to the selected registration/provider, rather than silently trying alternative scopes or clients after rejection.

## Compatibility flow to implement

1. Generate 32 random bytes for OAuth state and an RFC 7636 verifier; base64url without padding. Challenge = base64url(SHA256(ASCII(verifier))). Keep pending state/verifier only in memory. Generate or retrieve a persistent P-256 private key and device UUID from this application's Keychain entries. Never inspect another app's credential store.
2. POST `https://device.auth.xboxlive.com/device/authenticate`, JSON `RelyingParty:http://auth.xboxlive.com`, `TokenType:JWT`, Properties `{AuthMethod:ProofOfPossession, Id:{device-uuid}, DeviceType, Version, ProofKey:JWK}`. Headers include contract version `1` and the signed message below. Public JWK is `{kty:EC, crv:P-256, alg:ES256, use:sig, x, y}`; x/y are 32-byte big-endian coordinates, base64url without padding.
3. POST `https://sisu.xboxlive.com/authenticate`, signed JSON `{AppId,TitleId,RedirectUri,DeviceToken,Sandbox:RETAIL,TokenType:code,Offers:[xboxlive.signin,offline_access],Query:{code_challenge,code_challenge_method:S256,state}}`. Retain `X-SessionId`; open the returned `MsaOauthRedirect` URL only after checking HTTPS and an exact allowed Microsoft/Xbox hostname. Verified on 2026-10-12: this normal begin flow currently returns `sisu.xboxlive.com`, with a `/client/v68/<public-client-id>/view/splash.html` path and a query parameter named `msa`. Only scheme, host, path, field/header names, and query names were recorded; no query values or tokens. This first-party SISU frontend is now allowed alongside `login.live.com` and `login.microsoftonline.com`. UI owns browser presentation and callback capture.

   The [public Microsoft splash bundle](https://sisu.xboxlive.com/client/v68/000000004825FC1F/shared/splash.bundle.js), fetched without query values or credentials, reads `msa` through `URL.searchParams` and assigns that service-supplied URL to `window.location` when the user presses Continue. It does not require a native authentication XAL bridge at this stage; its sole `__xal__` symbol supplies accessibility focus. Preserve this normal navigation instead of rebuilding or rewriting authorization parameters. The safe redirect diagnostic contains no query values, authorization codes, or tokens. Public splash HTML and JavaScript are retained for source verification.
4. Accept a callback only when scheme/host/port/path exactly match the configured redirect, and a single `state` exactly matches the pending value. Reject duplicate code/state/error parameters, fragments, absent state/code, cancellation, and callback reuse. Do not extract credentials from a page or read browser cookies. Redeem only the callback code.
5. POST form data to `https://login.live.com/oauth20_token.srf`: `client_id`, `code`, `code_verifier`, `grant_type=authorization_code`, the same `redirect_uri`, and selected scope set. Public native clients send no `client_secret`. Preserve the raw Microsoft access token separately; add `d=` only when constructing the Xbox/SISU request.
6. Obtain a fresh device token using the same persistent key/UUID, then signed POST `https://sisu.xboxlive.com/authorize`: `{AccessToken:d=<msa-token>,AppId,DeviceToken,Sandbox:RETAIL,UseModernGamertag:true,SiteName:user.auth.xboxlive.com,RelyingParty:http://xboxlive.com,SessionId,ProofKey}`. Parse `UserToken`, `TitleToken`, their `NotAfter`, and user display claims. A new token is refresh, not identity rotation.
7. POST `https://xsts.auth.xboxlive.com/xsts/authorize` with `{RelyingParty,TokenType:JWT,Properties:{UserTokens:[user-token],DeviceToken,TitleToken,SandboxId:RETAIL}}`. HaloCache omits a request-signature header for this user/title/device exchange; do not confuse this observed behavior with the separately documented service-to-service signing requirements. Keep each returned XSTS token bound to its exact relying party and expiry.
8. Request `http://xboxlive.com` for identity display; use `DisplayClaims.xui[].xid` as decimal XUID and `gtg` as gamertag when present. Keep identifiers as strings, not floating-point numbers. A missing gamertag can be fetched through the user's own Xbox profile after ordinary authentication; it must never be invented or treated as the permanent identity. User hash `uhs` belongs to the particular token. Header form is `XBL3.0 x=<uhs>;<raw-token>`.
9. Request XSTS for `rp://playfabapi.com/`, then POST `https://ee38.playfabapi.com/Client/LoginWithXbox` with `{TitleId:EE38,XboxToken:<formatted-XSTS>,CreateAccount:true}`. Validate HTTP success and the PlayFab envelope. Parse `data.SessionTicket`, `data.EntityToken.EntityToken`, `data.EntityToken.Entity.Id`, `data.EntityToken.TokenExpiration`, and `data.PlayFabId`. [Microsoft's API](https://learn.microsoft.com/en-us/rest/api/playfab/client/authentication/login-with-xbox?view=playfab-rest) documents these credentials. [The native SDK's Xbox login](https://learn.microsoft.com/en-us/gaming/playfab/api-references/c/pfauthentication/functions/pfauthenticationloginwithxboxasync) is available on macOS; this establishes platform capability, not MCC authorization.

## Exact signing primitive

Source: [HaloCache `_sign`](https://github.com/HaloCache/halo-mcc-auth/blob/50c5054805b5f52fafc2ddcb8aeaa1f97d149443/src/sisu-auth.js#L180), cross-checked with Microsoft's [proof-key protocol](https://learn.microsoft.com/en-us/gaming/gdk/docs/services/fundamentals/s2s-auth-calls/s2s-calls/live-title-service-calls-xbox-live?view=gdk-2510).

For the observed policy version 1, no extra headers, complete body:

```text
preimage = BE32(1) || 00 || BE64(filetime) || 00
         || ASCII(UPPERCASE(method)) || 00
         || ASCII(percentEncodedPath + optional "?" + percentEncodedQuery) || 00
         || ASCII(Authorization header value or "") || 00
         || exactBodyBytes || 00
filetime = (floor(unixSeconds) + 11644473600) * 10000000
signature = ECDSA_P256_SHA256(preimage), raw 32-byte BE r || 32-byte BE s
Signature header = Base64(BE32(1) || BE64(filetime) || signature)
```

Do not include hostname, add a spurious extra-header separator, sign one JSON encoding and send another, or use DER signature bytes. Serializing JSON once to Data and signing/sending the same Data avoids whitespace/key-order errors. CryptoKit's P256 signature `rawRepresentation` supplies the 64-byte format. Other endpoints may impose a different policy; this primitive is not an authorization bypass or a claim that all Xbox requests share one policy. The fixture records expected unsigned preimage bytes, not a service-valid signature.

## Refresh, storage, and errors

Legacy refresh POST goes to the same Live token endpoint with configured `client_id`, `grant_type=refresh_token`, refresh token, and original scopes. Replace the refresh token if a new one is returned, otherwise preserve the prior value. Recreate a SISU session and fresh device token, then reacquire Xbox/XSTS and PlayFab credentials. Use each service's returned expiry with a small safety margin; do not assume universal four-hour or five-minute validity. Serialize refresh operations to prevent concurrent token replacement races.

Only this app's Keychain stores the refresh/session envelope and persistent P-256 private key. OAuth pending state, authorization codes, and Xbox user/title/XSTS intermediates stay in memory. No raw request/response/token logging. Sign-out removes this app's stored session and identity, and clears pending state. A denied scope, account restriction, HTTP 401/403, invalid refresh, or refused identity produces a useful stage/status error and stops; do not try other clients, rotate keys/device IDs, or strip required claims after denial.

## MCC credentials and discovery

Saved binary evidence confirms `x-auth-token` is the PlayFab **SessionTicket**, and `EntityToken` is `data.EntityToken.EntityToken`; Spartan token is separate. See the authentication provenance report (historical file: `../investigation/research/static/mcc-upload-analysis.md`; absent from this checkout). Never interchange these values.

Spartan acquisition, if needed for service discovery/settings, uses XSTS RP `https://prod.xsts.halowaypoint.com/`, then POST `https://settings.svc.halowaypoint.com/spartan-token` with `{Audience:urn:343:s3:services,MinVersion:4,Proof:[{TokenType:Xbox_XSTSv3,Token:<raw-XSTS>} ]}`. Parse `SpartanToken` and `ExpiresUtc.ISO8601Date`; send it as `X-343-Authorization-Spartan` only to the appropriate Halo service.

Public HaloCache constants hardcode PlayFab `EE38` and some MCC URLs. The binary instead assembles discovered endpoint URLs from `Endpoints[name].AuthorityId`, `Authorities[id].Hostname`, and endpoint `Path`, in initializer `0x1402ed84c` (historical file: `../investigation/research/ghidra-targeted/mcc-auth-addition/0x1402ed84c.c`; absent from this checkout). Service names relevant to publication are `MCCAzureFunctions_UploadFile`, `MCCAzureFunctions_GetUploadPermission`, and `MCCAzureFunctions_GetFileSharePublicKeys`.

Binary task `0x1402c7eb4` builds `https://{PlayFabTitleId}.playfabapi.com/Client/GetTime` and an `X-Authentication` header. Current [official GetTime](https://learn.microsoft.com/en-us/rest/api/playfab/client/title-wide-data-management/get-time?view=playfab-rest) requires `X-Authorization:SessionTicket` and normally returns `data.Time`, not an endpoint map. Subsequent binary/resource tracing resolved actual discovery: public GET `https://settings.svc.halowaypoint.com/settings/hmccpc/9d6dbeddd8bc478f92c6a6fac6424ca7` returned an Endpoints/Authorities map without authentication. The authoritative map resolves the three publishing routes to `mcc-production.azurefd.net/api/{UploadFile,GetUploadPermission,GetFileSharePublicKeys}`; see `official-service-config-2.json` and `official-discovery-read-results.json`. No Spartan acquisition is required for this public discovery document. A plain GetTime success still must not count as successful upload-endpoint discovery.

## Implementation contract and validation

Native files: `AuthModels.swift`, `AuthService.swift`, `XboxRequestSigner.swift`. Interface is actor `AuthService` with begin/complete/restore/signOut; complete returns string XUID, gamertag, PlayFab SessionTicket, entity token/entity ID, and expiry. Configuration governs all identity fields consistently. Deterministic tests cover PKCE, preimage bytes, P-256 raw signature verification, URI/state rejection, and no HTTP use for invalid callbacks.

Implemented and compiled with the native Swift toolchain. `AuthTests.swift` supports XCTest when available and a `-D AUTH_STANDALONE_TESTS` executable runner otherwise. The standalone runner passed RFC PKCE, exact unsigned signing fixture, raw signature verification, altered-body rejection, query/Authorization inclusion, public JWK coordinates, callback URI/state/duplicate rejection, provider refusal classification, and unsolicited-callback rejection. These checks made no live authentication calls and accessed no Keychain entries.

Offline completion does not establish a live user-authenticated session, accepted custom app identity, or successful File Share publication. The authorized device/SISU-begin diagnostic verified the returned browser host, without user credentials, Xbox user/XSTS exchange, or PlayFab login. Public settings discovery was separately verified by the binary worker. The next user-authenticated check must be explicit interactive sign-in and an ordinary authorized read/session check, with refusal respected.
